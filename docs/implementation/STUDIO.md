# Research Studio implementation and verification

Research Studio is the local authoring workspace at `/studio.html`. Investigate and Research Lab link to it with the applied study context. The four main destinations remain Explore (`atlas.html`), Investigate (`investigate.html`), Research Lab (`research.html`) and Evidence (`evidence.html`); Studio is a connected authoring workspace. The landing page and its frozen October 1 globe release remain protected.

This is an implementation record, not a declaration that every master-prompt gate is closed. The local authoring and export path is exercised here; externally managed SDK/host gates remain explicitly separate.

## Connected workflow

1. Open `studio.html?case=park-2024` and choose **Build from current study**. The seven-card starter freezes authentic replay, missingness and original-row receipts. The browser checks preserve 6,224 eligible unique records and 2,228 joint cell-days as distinct quantities.
2. Arrange cards, create durable groups, align or move grouped cards, save/restore a pan/zoom viewport, edit authored notes, link compatible contexts, or inspect a card through the keyboard outline. Offscreen previews load on approach or explicit selection. Brush a chart interval or inspect a common cell to focus compatible linked cards; these transient selections do not mutate the applied study, document revision or frozen receipts. Changes use owned, revision-checked transactions with undo/redo. Draft study dates and bounds do not calculate or replace evidence until applied. Changing a named preset's interval creates a custom selection; frozen evidence retains its original scope.
3. Select material in Story Director and create a six-chapter draft. Edit chapter order, duration, prose, captions, checked fields, date, sensor selection, bounded interval, highlighted cells, visible evidence-card gallery, audience profile, target duration, camera crop/transition and supplied local landscape layers. Save and resolve an immutable story revision. A camera crop affects display only; source counts retain their full frozen scope. The resolved scene contract is shared by the browser reader, local renderer and Remotion input.
4. Read the story, pause at a question, explore its frozen evidence through JARVIS and resume the same chapter. Deterministic source-state checks use the existing assistant orchestrator without a provider key. Typed JARVIS arrangement/story/workflow proposals require explicit application and reject a stale board revision. A workflow proposal loads a validated editor draft; saving and executing the recipe are separate explicit actions. Both server ownership/stale checks and mocked-inference DOM checks cover this path. Story chapters can also follow transcript scrolling; explore/resume keeps the exact saved chapter.
5. Export a self-contained reader ZIP. Serve its extracted folder with any static HTTP server. It includes prepared SVG scenes, dated local context images embedded in the scenes, receipts within explicit size limits, transcript, captions and checksums. It has no authoring API, private cookie, live terrain or model dependency.
6. Run a React Flow recipe. Both **Study to investigation board** and **Selected findings to story and video** use exact replay detail, retaining its 31-day/10,000-row limits. The graph can prepare checked cards, a real editable story draft and an export inventory. Applying an output is explicit; a recipe never silently renders, publishes or narrows the study. The browser QA runs the saved findings-to-story recipe on both Park and the authentic Camp study context. Other allowlisted operations, including single-month research, remain available as typed blocks.
7. Render the same saved scene revision through the configured video adapter. Captions-only rendering needs no model provider. Optional narration shares the existing assistant reservations, prices, ceilings and free-only restrictions; no separate paid model loop was introduced.

## Architecture and data contracts

The Python/SQLite scientific pipeline is unchanged. `fireatlas/studio/` adds a separate durable SQLite store, normally under `data/studio/`, for principals, boards, inverse transactions, frozen result snapshots, story revisions, workflow runs, render jobs, assets and room roles. The optional assistant store remains separate. The local authoring principal uses an HttpOnly, SameSite cookie; same-origin mutation checks and server-side ownership apply to each route.

`studio-app/` is a React/TypeScript/Vite island. Its checked build goes to `fireatlas/static/studio-assets/`, with a hash manifest and served-file allowlist. A tldraw 5.5.2 adapter registers evidence shapes holding card IDs and geometry; authoritative values stay in verified receipts. It lazy loads only with an operator-supplied public SDK license key. Without that key, the built-in board and outline remain usable. React Flow 12.12.0 lazy loads the workflow composer; a keyboard/table editor exposes the same graph.

The map reuses the existing fixed-width Gaussian kernel and study-fixed normalization for occupied-cell heat. Persistence and single-source peak native FRP use separate units and domains. Source hiding and frame changes do not recalculate a scale. Joint FRP is refused. Prepared maps show common-cell centers and explicitly label their schematic scope. Complete zero-record days, incomplete exports and processing gaps remain distinct in source evidence.

One `fireatlas-resolved-story-v1` model supplies the web story, portable reader, MCP preview and video renderer. New scene figures use version 2: camera crops transform geographic geometry while headings, units and legends remain stationary. Interval maps say occupied common cell-days; single-date maps say occupied common cells. Version 1 figures still reproduce their original frozen bytes, so existing reader verification remains compatible. Camera movement never interpolates measurements. Snapshots preserve operation, exact context, eligibility/method/unit, release identity, original calculation receipt hash and limits. The portable-reader verifier checks entry paths and expansion limits, recalculates cited facts and redraws prepared figures from bundled receipts. Tests forge a number or SVG and refresh every checksum; scientific/figure verification still rejects them. Embedded context-layer PNG bytes retain exact footprint, product version and dated provenance; verification does not consult the current context manifest. This is computational consistency, not independent scientific review.

## Build and startup

Core local launch remains:

```bash
uv sync --frozen
bash scripts/run_website.sh
```

Build frontend modules from locked dependencies:

```bash
(cd studio-app && npm ci && npm run build)
(cd studio-mcp-app && npm ci && npm exec tsc -- --noEmit && npm run build)
(cd studio-render && npm ci && npm test)
python3 scripts/refresh_static_assets.py --site site
python3 scripts/check_landing_preservation.py
```

The refresh tool preserves protected landing files and the separate analytical snapshot. SDK builds already use relative asset URLs and retain their manifest bytes during subpath rebasing. Static hosting supports exported readers and named analytical evidence; private authoring requires the Python service and is clearly reported unavailable.

For the locally exercised silent render engine, install Node.js, Chromium (or Google Chrome) and `ffmpeg`, then explicitly enable:

```bash
FIREATLAS_STUDIO_LOCAL_RENDER=1 uv run python -m fireatlas.web --no-showcase
```

Its manifest identifies `local-svg-ffmpeg` with `rasterizer: chromium`. Chromium rasterizes controlled local SVG scenes; the local adapter uses three camera keyframes per scene. This is a schematic documentary adapter. It is distinct from the Remotion adapter, whose bundle compiles but whose licensed rendering remains unverified. Actual frame review caught an ImageMagick clipping defect; the exercised adapter now uses Chromium and preserves map bounds and fixed labels. Remotion 4.0.532 is implemented in `studio-render/entry.jsx` and `render.mjs`, using prepared scenes and bounded local narration assets. The operator must independently establish license eligibility or hold the applicable license, then set `FIREATLAS_REMOTION_LICENSE_ACK=free-eligible` or `company-license`. No license eligibility was assumed during tests. See [Remotion's license guidance](https://www.remotion.dev/docs/license/pricing).

The tldraw adapter needs `FIREATLAS_TLDRAW_LICENSE_KEY=<public-sdk-license-key>`. This public SDK key is the only licensing value sent to the browser; provider keys and collaboration secrets remain server-side. See [tldraw licensing](https://tldraw.dev/community/license).

For managed rooms, configure `LIVEBLOCKS_SECRET_KEY=<server-secret>` and a declared `FIREATLAS_STUDIO_ORIGIN=https://your-origin.example`. The default Liveblocks adapter authorizes only the exact room and current member role. The official Liveblocks 3.24.3 client carries presence, cursors, revision hints and a field-level `LiveMap`/`LiveObject` layout draft. Moves and resizes on different coordinate fields merge, including gestures begun before another editor’s resize. The shared layout is a presentation draft: **Save merged layout** creates one role- and revision-checked reversible document transaction. Pending layout edits survive reconnect; saved-field conflicts retain the draft, and participant undo refuses to overwrite another editor’s change. Viewers only inspect the draft. Scientific rows, provider credentials and ownership tokens are not put in shared client storage. Card content, links and group membership continue through checked document edits, and concurrent story edits preserve explicit revision conflicts. Comments can cite a card or an exact saved chapter revision. This implementation follows the [official Liveblocks Storage API](https://liveblocks.io/docs/api-reference/liveblocks-client); hosted transport verification remains pending. `FIREATLAS_STUDIO_COLLAB=loopback` is explicitly process-local development/QA, not hosted collaboration.

Install the isolated assistant dependencies to run the existing private stdio MCP server. `studio-mcp-app/` builds the official MCP Apps extension 2.0.3 SDK resource at `ui://fireatlas/studio/app.html`. FastMCP negotiates `io.modelcontextprotocol/ui`; a client without that extension still receives text/JSON. Board/card/story tools use the same owned Studio service. There is no public unauthenticated listener. See [MCP Apps quickstart](https://apps.extensions.modelcontextprotocol.io/api/documents/quickstart.html).
